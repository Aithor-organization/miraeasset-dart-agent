## 1. 제안 요약

**한 문장**: 공시의 숫자는 **조회**하고 문장은 **생성**하는, 근거 추적이 구조적으로 보장된 공시 분석 Agent.

일반적인 공시 RAG는 "문서를 잘 찾아 LLM에게 읽히는" 문제로 접근한다. 그러나 이 코퍼스를 실측한 결과,
**DART 공시는 이미 기계 판독 가능한 구조를 갖고 있다**:

| 발견 | 의미 |
|---|---|
| 재무제표 셀에 **XBRL 인라인 태깅** (`<TE ACODE="dart_OperatingIncomeLoss" ACONTEXT="CFY2024dFY_…ConsolidatedMember">`) | 「2025년 **연결기준** 매출액」은 **읽고 추측할 문제가 아니라 조회할 문제**다 |
| 계약·지분·자금조달 공시가 **완전 정형 key-value** | 유형별 집계가 SQL로 정확히 계산된다 |
| 정기공시가 **동일 법정 목차** (12개사·10섹터 교차검증 완료) | 「분기보고서 기준 투자 계획」을 **주소로 직접 지정** 가능 (검색 불필요) |
| 정정공시가 **원본 포인터 + 정정전/후 diff 표**를 자체 보유 | 「변경 이력 분석」이 추론이 아니라 **그래프 탐색**이 된다 |

그래서 우리는 검색 성능 경쟁이 아니라 **표현 계층 경쟁**을 택한다.
LLM에게 표를 읽히지 않고, **먼저 사실(fact)로 정규화한 뒤** LLM에게는 해석과 설명만 맡긴다.

```
      일반적 접근                              본 제안
  질의 → 벡터검색 → 표 덩어리를          질의 → 사실 조회(SQL) + 섹션 주소 지정
        LLM에 투입 → 숫자 생성                 → 수치는 슬롯 주입, 문장만 생성
                                              → 결정론적 검증기 통과 후 응답
  ⚠ 숫자 오독·환각이 LLM 내부에서        ✅ 숫자 오류가 구조적으로 발생 불가
     발생하고 검출 불가                       (틀리면 검증기에서 차단)
```

## 2. 문제 정의

### 2-1. 과제가 실제로 요구하는 것

주최측 참고용 질의 6종을 역산하면, **4종이 단일 문서 검색으로 풀리지 않는다.**

| 질의 | 겉보기 난이도 | 실제 병목 |
|---|---|---|
| "2025년 **연결기준** 매출액" | 쉬움 | 연결/별도 혼동 · 기수(제57기) ↔ 회계연도 매핑 · 백만원 단위 |
| "2026년 1분기 보고서 기준 주요 투자 계획" | 보통 | **문서·섹션 특정** — 벡터 유사도로는 정확 지정 실패 |
| "2차전지 기업 A와 B 중 2025년 설비투자 규모가 더 큰 곳" | 보통 | **섹터→기업 해석** + 동일 지표 정규화 + 비교 판정 |
| "2025년 자금조달 내역을 유형별(유상증자·CB·BW·EB)로" | 어려움 | **이벤트 유형 집계** — 25종 주요사항보고서 분류 필요 |
| "2025년 체결 계약 중 이후 **해지된** 계약이 있는가" | 어려움 | **이벤트 간 링크** — 체결↔해지 쌍 추적 |
| "2023 vs 2025 사업보고서 핵심 사업 변화" | 어려움 | **동일 섹션 시계열 정렬** 후 대조 |

### 2-2. 그리고 여기에 함정이 있다

실측에서 드러난, **미처리 시 조용히 오답을 만드는** 요인들:

| # | 함정 | 미처리 시 결과 |
|---|---|---|
| 1 | 거래소공시 1,469건이 `.xml` 확장자이나 실제 **HTML**이고, meta는 `euc-kr`을 선언하지만 **바이트는 UTF-8** | 표준 파서(BeautifulSoup·pandas.read_html) 사용 시 **1,469건 전부 문자 파괴** |
| 2 | 거래소공시 **정정 비율 43%** (631/1,469) | 원본+정정본 중복 집계 → 「2025년 계약 총액」 **체계적 과대계상** |
| 3 | 질의는 **통용명**("현대차")으로 오지만 조인 키는 **법인명**("현대자동차") | 조회 실패. KT→케이티, 엔씨소프트→NC, LIG넥스원→LIG디펜스앤에어로스페이스 |
| 4 | XBRL 태깅률이 균일하지 않다 (annual 60% / half·quarter 28%) | XBRL 단독 의존 시 반기·분기 질의에서 **수치 미회수** |
| 5 | 텍스트 총량 400M chars 중 **95%가 정기공시**, 그 내부 상위 7섹션(47%)이 인명·계열사 **레지스트리 표** | 전량 임베딩 시 비용 폭증 + 노이즈 증가. 크레딧 초과는 **자기 부담** |
| 6 | 공시에 임원 **생년월일·성별**이 포함되어 있다 (`PSN_BIH`/`PSN_SEX`) | 그대로 노출 시 평가지표 6(안전성) 실점 |
| 7 | 금액 **단위가 문서마다 다르다** — 원 / 천원 / 백만원 혼용, 표본 **27%는 단위 미표기** | 「A사 vs B사 설비투자 비교」에서 **1,000배 오차**. 가장 발견하기 어려운 오답 유형 |

> **이 7개 함정을 아는 것 자체가 설계 자산이다.** 대부분은 개발 중반에 발견되어 재작업을 유발하는 종류다.
> 특히 #7(단위 혼용)은 **답변이 그럴듯해 보이면서 1,000배 틀리는** 유형이라 테스트 없이는 발견되지 않는다.
> 본 제안은 조사 단계에서 전부 확인하고 대응을 명세에 반영했다 (기술명세서 Stage D · R5b).

### 2-3. 평가지표가 말하는 진짜 요구

응답 스키마에 `retrieved_context`와 `think_trace`가 **포함되어 있다.** 즉 이 두 필드는
디버그 로그가 아니라 **채점 대상 산출물**이다 — 지표 2(근거 완전성)·5(추론 논리성)가 여기서 채점된다.

그리고 지표 7은 특이하다:

> **정보한계 대응** — 보유 데이터로 답변할 수 없는 질의를 식별하고, 무리한 답변 대신 한계 고지 또는 필요한 정보를 역질문으로 대응하는가

**답을 잘 하는 능력이 아니라, 답하지 않을 줄 아는 능력을 본다.**
평가문제에 답변 불가 문항이 의도적으로 섞여 있을 것으로 판단한다 (난이도 상/중/하 × Closed/Open 혼합).
→ 그래서 우리는 자체 평가셋에 **Abstention 함정 15문항**을 처음부터 넣는다 (§5-2).

## 3. 제안 방법

### 3-1. 3계층 데이터 표현

```
L1  Fact Store       재무 사실 · 계약/자금조달/지분 이벤트 · 정정 체인 · 레지스트리
    (SQLite)         → 수치·집계·비교·순위를 SQL로 결정론 처리
                     
L2  Section Store    법정 목차 주소(II-1, III-2-2 …)로 접근하는 섹션 트리 + 표 markdown 보존
                     → 문서·섹션 특정 질의를 검색 없이 직접 조회 / 시계열 대조의 정렬 축
                     
L3  Retrieval Index  BM25(Kiwi 형태소) + bge-m3 벡터 → RRF 융합 → CLOVA Reranker
                     → 위 두 계층으로 닿지 않는 서술형 질의만 담당 (선별 임베딩)
```

**핵심은 우선순위다**: `주소 지정 → 사실 조회 → 검색`. 검색은 최후 수단이지 첫 수단이 아니다.

#### 이 우선순위에는 외부 검증이 있다

우리가 코퍼스 실측에서 독립적으로 도달한 「주소 우선」 원칙은 **PageIndex**(VectifyAI, MIT, 25.4k★)의
*Vectorless RAG* 와 동일 사상이고, **금융 문서 벤치마크에서 정량 검증**되어 있다:

| | 벡터 RAG | PageIndex (계층 트리 + LLM 탐색) |
|---|---|---|
| **FinanceBench 정확도** | ~80-90% | **98.7%** |
| 문서 구조 | 청킹으로 파괴 | 계층 보존 |
| 설명 가능성 | 유사도 점수만 | **페이지/섹션 단위 추적** ← 지표 2 요구사항과 일치 |

그리고 **우리는 PageIndex의 유일한 약점을 회피한다.** PageIndex의 주 비용은 트리를 LLM으로 구축하는
것이고(SKILL.md가 "인덱싱 비용이 높음"을 한계로 명시), 잘 구조화된 문서를 전제한다.
**본 코퍼스는 트리를 이미 갖고 있다** — `<TITLE>` 태그가 법정 목차를 그대로 보존하므로
트리 구축이 **LLM 없이 결정론적 파싱**으로 끝난다. 정확도 이점은 취하고 비용 단점은 제거하며,
이는 R2(크레딧 초과) 완화에도 직접 기여한다.

> ⚠️ 라이브러리를 그대로 쓰지는 않는다 — PDF 입력 전제 + `litellm` 의존이 HCX 전용 제약과 어긋난다.
> **사상만 차용**한다. 또한 98.7%는 **영문 문서·타 모델(Mafin 2.5) 기준**이므로 한국어 DART + HCX-007에
> 그대로 전이된다고 보지 않는다 `[추정]`.

### 3-2. 6개 도구를 쓰는 Agent

HCX-007의 Function Calling으로 도구를 선택·연쇄한다.

| 도구 | 역할 |
|---|---|
| `fact_query` | 재무 지표 결정론 조회 (수치 질의는 **반드시** 이 경로) |
| `get_section` | 목차 주소로 섹션 원문 직접 조회 |
| `doc_search` | 하이브리드 검색 (위 두 경로 실패 시) |
| `event_query` | 계약·자금조달·지분 이벤트 유형별 집계 (정정 반영 유효본만) |
| `trace_chain` | 정정 체인 / 계약 체결↔해지 / 지분 변동 이력 추적 |
| `compute` | 증감률·비중·순위·합계 — **LLM은 산술을 직접 하지 않는다** |

`compute`의 인자는 **숫자가 아니라 `fact_id` 참조**다. LLM이 숫자를 프롬프트로 옮겨 적는 순간
전사 오류가 발생하므로, 계산은 서버가 DB 값에 대해 수행한다.

### 3-3. 환각을 "탐지"하지 않고 "발생 불가"로 만든다

Synthesizer는 **수치를 쓸 수 없다.** 자리표시자만 생성하고, 서버가 DB 값으로 치환한다.

```
LLM 생성:  "2025년 연결 매출액은 {{F12345.value}}{{F12345.unit}}입니다. [C1]"
서버 치환:  "2025년 연결 매출액은 300,870,903백만원입니다. [C1]"
```

그 뒤 **LLM을 쓰지 않는 결정론 검증기** 5종을 통과해야 응답이 나간다:

| 검증 | 내용 | 담당 지표 |
|---|---|---|
| V1 | 모든 수치가 fact 치환 결과이거나 context 내 존재 | 1·4 |
| V2 | 모든 인용 마커 `[Cn]`이 실제 citation에 존재 | 2·4 |
| V3 | 질의 요구사항 체크리스트 전 항목 대응 문장 존재 | 3 |
| V4 | 금지 표현(미래예측·투자의견·목표주가) 부재 | 6 |
| V5 | Abstention 조건 판정 | 7 |

> 검증기가 LLM이면 환각을 환각으로 검증하게 된다. 그래서 검증기는 전부 코드다.

### 3-4. 플랫폼 제약을 제약이 아니라 자산으로

CLOVA Studio는 **Reranker API와 RAG Reasoning API를 플랫폼 차원에서 제공**한다.

| 조사 결과 | 설계상 이득 |
|---|---|
| HCX-007: 128K 컨텍스트 · Function Calling · Structured Output · Thinking 전부 지원 | Agent 오케스트레이션 기반 모델 확정. 별도 프레임워크 불필요 |
| **Reranker API** (`/v1/api-tools/reranker`) | 외부 리랭커(Cohere/BGE) 없이 2-stage 검색 → **"HyperCLOVA X만" 제약 위반 위험 제거** |
| **Embedding v2 = bge-m3** (8,192토큰 / 1024차원) | 공시 청크 길이에 적합 (clir 계열 500토큰은 부적합) |
| **OpenAI 호환 엔드포인트** (`/v1/openai/`, `tools`·`tool_choice`·`response_format` 지원) | OpenAI SDK·LangChain을 그대로 사용하며 LLM은 HyperCLOVA X만 사용 |

> 💡 R1 회피 설계: "LLM은 HyperCLOVA X만"이 임베딩·리랭커를 포함하는지 **PDF에 명시가 없다.**
> 우리는 처음부터 임베딩·리랭킹도 CLOVA API로 통일해 **해석 여하에 무관하게 안전한** 구성을 택한다.
> 08.06 설명회에서 확인하되, 확인 결과가 어느 쪽이든 재작업이 발생하지 않는다.

## 4. MVP 범위

### 4-1. In Scope (제출 필수)

| # | 항목 | 완료 정의 (DoD) |
|---|---|---|
| S1 | 파서 4종 (periodic/major/holding/exchange) | 4,204문서 전수 파싱, 실패 문서 목록 명시 (침묵 실패 금지) |
| S2 | Fact Store 구축 | `fin_fact` / `contract_event` / `capital_event` / `holding_event` / `correction_diff` / `registry_row` 적재 완료 |
| S3 | 기업 별칭 4-way 정규화 | 70개사 × (법인명·통용명·영문·종목코드 + 수기 변형) 무결성 테스트 통과 |
| S4 | 정정 체인 해소 | `supersedes_doc_id` / `is_effective` 설정, 매칭률 실측 리포트 |
| S5 | Section Store + 표준 주소 사전 | 정기공시 1,054건 섹션 트리 + 10종 주소 매핑 |
| S6 | 하이브리드 검색 | BM25(Kiwi) + bge-m3 + RRF + CLOVA Reranker 동작 |
| S7 | Agent 6개 도구 + Planner | 질의 유형 T1~T6 전 경로 동작 |
| S8 | Verifier V1~V5 + Abstention Gate | 결정론 구현, LLM 미사용 |
| S9 | `GET /answer` API | 계약 4필드 정확 준수 + 부가 필드, 500 미발생 |
| S10 | 자체 평가셋 180문항 + 채점 러너 | 지표 7종 자동 산출 |
| S11 | 배포 (Public 망) + 상시 가용 | `/health` 모니터 + 자동 재시작 + 크레딧 계측 |
| S12 | 제출물 3종 | 소스코드+Dockerfile+README / 기술제안서 / API 명세 |

### 4-2. Out of Scope (MVP 제외 — 본선 이후 검토)

| 제외 항목 | 제외 이유 |
|---|---|
| GraphRAG (엔티티 지식그래프) | 정정 체인·계약 생애주기는 **관계형 링크로 충분**하다. 그래프DB 도입은 38일 대비 ROI 미달 |
