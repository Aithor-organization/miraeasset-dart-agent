02

규칙

넘으면 실격이다. 설계 자유도보다 먼저 확인해야 하는 경계.

실격 조항

LLM은 HyperCLOVA X만 사용 가능하다. 그 외 모델 사용 시 평가대상에서 제외된다.

Gemini·GPT로 답변을 생성하면 아무리 잘 만들어도 채점받지 못한다. 단, 개발 도구로 다른 모델을 쓰는 것은 무관하다 — 제출물의 런타임에 들어가면 안 된다는 뜻이다. 코드를 어떤 AI로 짜든 상관없지만, 서버가 답변을 만들 때 호출하는 LLM은 HCX여야 한다.

해석이 갈리는 지점 — 아직 안 풀렸다

요강은 “LLM은 HyperCLOVA X만”이라고만 쓰고, 임베딩·리랭킹 모델이 “LLM”에 포함되는지, 전처리 단계에도 적용되는지는 명시하지 않는다.
08-11 질의 결과 — 답을 받지 못했다

“전처리 과정에서 HyperCLOVA X 이외 모델을 써도 되는가”를 물었으나, 답변은 “공지사항을 참고 부탁드립니다”였다. 공지사항은 전처리/생성을 구분하지 않으므로 이 질문은 실질적으로 미해결이다 미확인.

반면 형태소 분석기·규칙 기반 NLP 라이브러리는 제한이 없다고 명확히 답변됐다. 즉 “모델”과 “규칙 기반 도구”는 다르게 취급된다 — 경계는 여전히 모호하지만 규칙 기반 쪽은 안전지대에 있다.

다행히 우리 설계는 가장 엄격한 해석에서도 안전하다.

  • 전처리 — lxml·BeautifulSoup·정규식·Kiwi. 전부 규칙 기반이며 모델을 쓰지 않는다.
  • 검색 — BM25(통계) + 임베딩은 CLOVA bge-m3.
  • 생성 — HCX-007만.

즉 미해결 질문의 어느 쪽 답이 나오든 우리는 영향을 받지 않는다. 이것이 설계 원칙 D6(플랫폼 네이티브)의 실질적 이익이다 — 해석 리스크를 설계 단계에서 제거해 두면 공지를 기다릴 필요가 없다.

함정 1 — 확장자가 거짓말을 한다

거래소공시 1,469건은 .xml 확장자를 달고 있지만 내용은 HTML이다. 더 나쁜 건 인코딩이다. meta 태그는 charset=euc-kr을 선언하는데 실제 바이트는 UTF-8이다.

선언을 믿고 euc-kr로 디코딩하면 한글이 전부 깨진다. 예외가 나지 않고 깨진 문자열이 나오기 때문에, 파싱은 “성공”하고 검색만 조용히 실패한다. 코퍼스의 35%가 사라지는 셈이다.

대응 — parsers/exchange.py
# 선언을 무시하고 바이트를 UTF-8로 강제 디코딩
raw = path.read_bytes()
text = raw.decode("utf-8", errors="ignore")   # euc-kr 선언은 신뢰하지 않는다
soup = BeautifulSoup(text, "lxml")

회귀 테스트 test_exchange_korean_not_mojibake가 이 경로를 지킨다.

함정 2 — 정정 공시 43%

거래소공시 1,469건 중 정정 diff가 2,515건 존재한다. 같은 계약이 원본과 정정본으로 두 번 들어 있다는 뜻이다.

정정 체인을 해소하지 않고 SELECT SUM(amount)을 하면 같은 계약이 중복 계상된다. “2024년 총 계약 규모”를 물으면 실제의 1.4배가 나온다. 청킹 + 임베딩만 하는 파이프라인은 이 문제의 존재 자체를 알 수 없다.

대응 — 유효본만 집계
document 테이블에 is_effective 플래그
  원본 → 정정본이 존재하면 is_effective = 0
  정정본 → is_effective = 1

모든 조회가 JOIN document d ON ... WHERE d.is_effective=1 을 거친다
FTS5 색인도 is_effective=1 문서만 담는다 (112,797 = 전량 일치)

함정 3 — 질의어와 조인 키가 다르다

사용자는 “현대차”라고 쓰지만 DB의 법인명은 “현대자동차”다. “하이닉스”는 “SK하이닉스”, “포스코”는 “POSCO홀딩스”, “네이버”는 “NAVER”다.

universe.csv의 listed_name ↔ corp_name ↔ corp_eng_name ↔ stock_code 4-way 별칭 테이블을 만들고, 자동 생성으로 안 잡히는 16종을 수기로 추가했다. 최종 별칭 232건, 미연결 0건.

부수 함정

corp_code(8자리)와 stock_code(6자리)는 문자열이다. pandas로 읽을 때 dtype={'corp_code':str}를 빠뜨리면 정수로 파싱되면서 선행 0이 유실된다. 00126380이 126380이 되어 조인이 전멸한다.

함정 4 — XBRL 태깅률이 균일하지 않다

사업보고서는 재무제표가 XBRL로 인라인 태깅돼 있어 기계 추출이 쉽다. 그런데 태깅률이 보고서 종류마다 다르다 — 사업보고서 약 60%, 반기·분기 약 28%.

XBRL만 믿으면 반기·분기 질의의 70%가 답을 못 찾는다. 그래서 표 파싱 폴백을 넣었다. III-1 요약재무정보 섹션을 앵커로 markdown 표를 파싱해 같은 fin_fact 스키마로 적재한다. source 필드에 xbrl / table을 기록해 출처를 구분한다.

함정 5 — 단위가 섞여 있다

금액 단위가 원 / 천원 / 백만원으로 섞여 있고, 표본의 27%는 단위 표기가 아예 없다.

단위를 무시하고 숫자만 비교하면 1,000배 오차가 난다. “A와 B 중 매출이 큰 곳은?” 같은 비교 문항이 전멸한다. §1의 대조표에서 POSCO홀딩스가 72,688,143,160,111 원, 삼성전자가 300,870,903 백만원인 것이 바로 이 문제다 — 둘 다 원 단위로 정규화해야 비교된다.

대응 — numbers.py
value_krw      원 단위로 정규화한 정본 값
raw_value      원문 그대로 (인용에 사용)
raw_unit       원문 단위 표기
unit_confidence  high | low   ← 미표기 시 low

# unit_confidence=low인 값은 비교·집계에서 거부한다.
# 틀린 답보다 기권이 낫다는 판단 (D5).
compute("compare", [a, b])  → refused: "단위 불확정"

회계 표기 음수도 처리한다 — (11,526,297)은 -11526297이다. 괄호를 못 읽으면 적자가 흑자로 뒤집힌다.

함정 6 — 공시에 개인정보가 있다

VIII-1 임원 및 직원 등의 현황 섹션에는 임원의 생년월일과 성별이 실제로 들어 있다. 공시 문서니까 “공개 정보”지만, 질의에 그대로 실어 보내면 채점 항목 중 개인정보 보호에서 감점된다.

PII 게이트를 두 겹으로 만들었다. ① 질의 자체가 개인 식별정보를 요구하면 기권, ② 섹션 본문을 반환할 때 생년월일·이메일·전화번호·주민번호 패턴을 마스킹.

과잉 차단 방지

“임원 수는?”·“임원 보수 총액은?”은 계속 답해야 한다. 회사 단위 정보까지 막으면 정확성과 근거 완전성에서 손해를 본다. is_pii_request()가 개인 단위 요구만 골라내고, 회귀 테스트로 두 방향을 모두 고정했다.

함정 7 — 누적과 당기가 공존한다

이게 가장 발견하기 어렵고, 가장 조용히 틀린다. 반기·분기 보고서의 XBRL은 같은 지표를 두 번 담는다 — 누적(연초부터)과 당기(해당 3개월).

구분은 ACONTEXT 속성에 인코딩돼 있다.

ACONTEXT 구조
<TE ACODE="..." ACONTEXT="CFY-dHYA-ifrs-full_ConsolidatedMember">

  CFY   당기 / PFY 전기 / BPFY 전전기
  d     duration (기간)  /  e  instant (시점)
  HY    반기  ·  FY 연간  ·  FQ·TQ 분기
  A     누적 (Accumulated)      ← 연초부터
  Q     당기 (Quarter)          ← 해당 3개월만

실측 — 두 배 차이

삼성전자 2025 반기 매출 — 누적(dHYA) 153.7조 vs 당기(dHYQ) 74.6조.

구분 없이 SELECT ... WHERE metric='revenue'를 하면 둘 중 아무 값이나 나온다. 어느 쪽이 나오든 “정상 동작”처럼 보이고, 절반은 오답이다.

초기 구현은 정규식이 FY만 인식해서 반기·분기 컨텍스트를 통째로 버리고 있었다. 문서당 3,000~4,000건씩 파싱 실패가 나던 것을 고치면서 period_scope 필드를 추가했고, 적재 사실이 14,466건 → 34,956건으로 늘었다. 약 2만 건이 되살아난 것이다.

환각을 탐지하는 대신 발생 불가로 만드는 여섯 가지 원칙과 그 구현.

D1 — 수치 결정론

수치는 LLM이 생성하지 않는다. 이게 전체 설계의 축이다.

보통의 RAG는 문서를 프롬프트에 넣고 LLM에게 “이 문서를 보고 답해”라고 시킨다. 이 구조에서는 LLM이 숫자를 읽어서 옮겨 쓰는 셈이라, 자릿수를 틀리거나 비슷한 다른 숫자를 가져올 여지가 항상 남는다. 확률을 낮출 수는 있어도 0으로 만들 수는 없다.

우리는 경로 자체를 없앴다. 계산 도구 compute()의 피연산자는 FactHit 객체만 받는다. 숫자 리터럴을 넣는 인터페이스가 존재하지 않는다.

D2 — 검색보다 주소

정기공시는 법정 목차를 따른다. 70개사 전부 동일한 구조다 — II-3 주요 투자 계획, III-2-2 연결 손익계산서처럼 내용의 위치가 규격으로 정해져 있다.

그렇다면 “주요 투자 계획”을 물었을 때 임베딩 유사도로 찾을 이유가 없다. 주소로 직접 가면 된다. 검색은 주소로 닿지 않는 서술형에만 쓰는 폴백이다.

이 판단은 외부 근거도 있다 — AI-research-SKILLs의 15-rag/pageindex가 제시하는 “Vectorless RAG”가 같은 사상이다. 다만 거기 인용된 성능 수치는 영문 코퍼스·다른 모델 기준이라 그대로 전이되지 않는다 추정. 차용한 것은 수치가 아니라 구조다.

D3 — 정정 우선

함정 2의 대응이 원칙으로 승격된 것이다. 조회 계층 전체가 is_effective=1을 통과하며, 정정 체인 해소는 인덱싱 시점에 끝난다. 런타임에 정정 여부를 판단하지 않는다 — 판단할 여지를 남기면 언젠가 빠뜨린다.

D4 — 근거는 로그가 아니라 산출물

응답의 retrieved_context와 think_trace는 디버깅용 부가 정보가 아니라 채점 대상이다. 요강의 평가 항목에 “근거 완전성”과 “추론 과정”이 명시돼 있다.

그래서 think_trace를 산문으로 쓰지 않고 구조로 만들었다.

왜 FTS5인가 — 배포를 막던 문제

초기 구현은 BM25를 파이썬 객체로 메모리에 상주시켰다. 6,504섹션 스모크에서는 잘 돌았다. 그런데 전체 코퍼스로 외삽해 보니 NCP 권장 서버(4GB)에 올라가지 않는다는 게 드러났다.

원인을 찾아보니 텍스트가 아니었다. Doc.text는 17MB로 전체의 3%에 불과했다. 진짜 원인은 (문서, 용어) 쌍 824,744개가 _tf(Counter)와 _postings(dict)에 이중으로 저장되면서 파이썬 객체 오버헤드를 무는 것이었다 — 쌍당 약 684바이트.

해법은 AI-research-SKILLs의 41-on-device-hybrid-search에서 왔다. 그 스킬이 제시하는 구성이 정확히 SQLite FTS5 + sqlite-vec다.

한국어를 FTS5에 넣는 법

FTS5에 Kiwi 형태소 분석기를 직접 붙일 수는 없다 — 커스텀 토크나이저는 C API가 필요하다. 그래서 색인 시점에 Kiwi로 분해한 토큰을 공백으로 이어 붙여 저장하고 unicode61 토크나이저로 색인한다. 질의도 같은 분해를 거치므로 형태소 단위 매칭이 그대로 유지된다.

FTS5의 bm25()는 k1=1.2 · b=0.75 고정이다. 설정 파일의 bm25_k1/bm25_b를 바꿔도 무시된다. 기본값과 같아서 실무상 무해하지만, 튜닝하려면 다른 방법을 찾아야 한다.

선별 색인 정책

모든 섹션을 같은 방식으로 색인하지 않는다. 볼륨의 47%를 차지하는 인명·계열사 나열 표는 제목만 색인한다 — 본문을 넣으면 노이즈만 늘고 검색 정확도가 떨어진다.

RRF 융합

BM25 랭킹과 벡터 랭킹을 합칠 때 Reciprocal Rank Fusion을 쓴다. 점수 스케일이 다른 두 랭킹을 순위만으로 합치기 때문에 정규화가 필요 없다.

retrieval/bm25.py — AITHOR rag.py와 동일 수식
score(d) = Σ  1 / (k + rank_i(d))        k = 60

AITHOR-Agent-Framework의 rag.py:_rrf_fuse가 같은 상수(k=60)로 구현돼 있어 검증된 구현을 그대로 차용했다. 벡터 랭킹은 임베딩 프로바이더가 없으면 건너뛰고 BM25 단독으로 동작한다 — 키 없는 환경 대응.

V1의 면제 규칙 — 여기가 까다롭다

“답변의 모든 숫자를 근거와 대조한다”를 순진하게 구현하면 연도·분기·날짜·섹션주소까지 검증 대상이 된다. 2024년의 2024, 2026-03-31의 03과 31, III-2-2의 숫자들이 전부 “근거 없는 수치”로 잡힌다.

그래서 면제 패턴을 두는데, 순서가 중요하다. 연도 패턴을 날짜보다 먼저 매칭시키면 2026-03-31에서 2026만 먹고 03·31이 남는다. 날짜 패턴을 먼저 놓아야 한다.

파생 표기가 근거 집합에 없어서 자기 자신의 결정론적 계산 결과를 환각으로 판정한 적이 있다. 300,870,903백만원을 사람이 읽기 좋게 300.9조원으로 바꿔 쓴 것이 근거에 없다는 이유로 문장째 삭제됐고, 답변이 비어버리자 V3까지 연쇄 실패했다.

고친 방법: 포맷 함수의 출력, str(value_krw), 계산 결과, 이벤트 건수를 모두 근거 집합에 미리 넣어둔다. 검증기를 느슨하게 만든 게 아니라, 결정론적으로 파생된 값도 근거임을 명시한 것이다.

설계 결정 — 500을 반환하지 않는다

어떤 입력에도 HTTP 500이 나가지 않는다. 모든 내부 예외를 잡아 기권 응답 + 200으로 변환한다. 평가 중 한 문항의 예외가 서버 장애로 보이면 나머지 문항까지 잃기 때문이다. 빈 질의만 400을 반환하며, 그 경우에도 계약 필드는 채워서 보낸다.

⚠️ 재시도 2회가 공지되면서 이 결정에 반대 논거가 생겼다. 500을 내면 2번 더 기회를 받는데, 200을 내면 그 답이 확정된다. 일시적 장애(예: CLOVA 순간 불통)에서는 500이 유리할 수 있다.

결론은 “둘 다 아니다”. LLM 호출이 실패하면 500도 기권도 아니라 결정론 템플릿으로 강등하는 것이 두 선택지보다 항상 낫다 — 수치·근거는 SQL에서 이미 확보돼 있으므로 답변의 핵심은 살아남는다. 현재 구조가 이미 그렇게 되어 있고(§7 강등 표), LLM 계층을 붙일 때도 이 원칙을 유지한다.

FTS5로 전환한 뒤에도 conftest.py가 여전히 인메모리 load_index()를 부르고 있었다. 부분 색인에서는 빨랐지만 전체 색인에서는 테스트가 8분간 멈췄다 — 29분·수 GB짜리 작업이었기 때문이다. 운영 경로(FTS5)로 통일했다.

서버 폴백이 OOM 경로였다

PII 마스킹이 명세에만 있고 구현이 없었다

기술명세서 §4-4에 마스킹이 요구사항으로 적혀 있었는데 코드가 없었다. “임원 생년월일 알려줘”가 섹션을 그대로 반환하고 있었다. agent/pii.py를 만들어 게이트 + 마스킹을 붙이고, 회사 단위 질의는 계속 답하는지 양방향 테스트로 고정했다.

15문항은 답하면 감점인 문항이다. 정답은 “적절한 사유와 함께 기권”이고, 그럴듯한 답을 지어내면 실패다. §11의 판단대로 채점 항목 셋에 동시에 걸리므로 비중 대비 가치가 높다.

정답 만들기

정답을 손으로 다 채우는 건 현실적이지 않다. 대신:

  • 수치 문항 — Fact Store에서 SQL로 정답을 뽑아 고정한다. 시스템이 스스로 채점 가능
  • 기권 문항 — 기대 abstain_reason 코드를 정답으로 둔다. 완전 자동 채점
  • 서술 문항 — 정답 문자열 대신 필수 포함 근거(섹션 주소)를 정답으로 둔다

이렇게 하면 180문항 중 150문항 이상이 자동 채점된다 추정. 반복 측정이 가능해야 개선 사이클이 돈다.
